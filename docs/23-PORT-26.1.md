# 23 — Port to Minecraft 26.1.2

Status: **spiked** (MNX-131, 2026-11-03). Target: Minecraft 26.1.2, NeoForge 26.1.2.126, Java 25. The spike measured the breakage (see Estimate); nothing is ported yet. This file is the plan and the ticket split (MNX-131 to MNX-140 in `14-BACKLOG.md`).

## Why 26.1.2 and not 26.2

26.2 exists, but the ecosystem a unification mod lives on is gathering on 26.1.2: KubeJS 8.x, JEI, the unofficial EMI port and the community Mekanism build are all built for 26.1.2, and the community Mekanism build says it will stay there. 26.1.2 is the likely next long-lived modpack version, as 1.21.1 was. Revisit if Mekanism or Create ship official builds for 26.2 only.

## Ecosystem state (checked 2026-10-30)

| Dependency | 26.1.2 | Consequence |
|---|---|---|
| NeoForge | 26.1.2.x (stable builds exist) | target |
| JEI | official build | MNX-013 can be ported |
| EMI | **unofficial** port only | MNX-014 waits for an official build or is kept on the unofficial one behind the adapter, never as a hard dependency |
| KubeJS | 8.0.x (beta) | bindings ported against 8.x; API to re-check before release |
| Mekanism | **community "Version Locked" build only** | no official recipe formats to test against |
| Create | **no official build** (unofficial "Create: Adapted") | same |
| IE, AE2, MI, Oritech, Silent Gear, Occultism, Extreme Reactors, Ex Deorum | not checked one by one | dev pack cannot be rebuilt as is |
| Almost Unified | not checked | arbitration (MNX-026) kept dormant if absent; already safe when absent |

**Rule for the port:** recipe formats (`data/materialnexus/material_nexus/recipe_formats/*.json`) are validated only against **official** builds. Unofficial ports may be used for smoke runs, never to change a format file: their recipe JSON can change when the official build lands, and a wrong format silently mis-unifies a pack.

## What breaks, measured on the code (main @ 151ec77, 132 files, ~14k lines)

Version in brackets is where the change happened between 1.21.1 and 26.1.2; exact API names are confirmed at compile time in MNX-131.

| Area | Where | Change | Weight |

What survives better than expected: the recipe text cache (MNX-115/116) reads recipe JSON from files, so classification and rewrite work on text, not on `Recipe` objects. `core/` (policy, resolution, domain) touches Minecraft almost only through `ResourceLocation` (registry access is limited to `core/discovery`), so it ports with the rename and its JUnit tests follow.

### Client recipes: the one real design question

The JEI viewer (route hover, recipe layouts) asks the client for a recipe by id. On 26.1.2 the client only has the recipe types the server chose to sync. Options, to decide in MNX-131 from what the spike shows:

1. **Rely on what JEI already syncs.** JEI needs the recipes too and asks NeoForge for them; the viewer looks recipes up in the set the client received. No new packet. Preferred if JEI syncs every type it displays.
2. **Ask NeoForge to sync the types Material Nexus shows** at datapack sync. Simple, but sends recipes to every client even without the GUI open.
3. **Targeted query packet** (recipe id → JSON) like the existing paginated GUI queries. Fits the "no periodic S→C stream" rule and the permission model; more code.

Not an option: a full recipe dump to the client on each reload.

**Decided (MNX-131): option 1.** Read in the JEI 26.1.2 jar (29.53.0.115): JEI asks NeoForge to sync only the vanilla types (`OnDatapackSyncEvent.sendRecipes` with crafting, smelting, smoking, blasting, campfire, stonecutting, smithing) and keeps what it receives from `RecipesReceivedEvent`. Each content mod syncs its own types for its own JEI categories. The viewer only draws a recipe a JEI category has registered (`MnxJeiPlugin.in`), so a recipe it can draw is always on the client. MNX-138 keeps the `RecipeMap` from the client `RecipesReceivedEvent` and replaces `level.getRecipeManager().byKey(id)` with `recipeMap.byKey(ResourceKey.create(Registries.RECIPE, id))`. A type nobody syncs has no layout, which the viewer already handles (`Optional.empty`). No new packet.

## Branches and maintenance

- `main` stays **1.21.1** until the release gate below; 1.21.1 is where the packs are.
- A long-lived integration branch `mc/26.1.2` is cut from `main` at MNX-131. Ticket branches start from it and merge back into it with the usual `MNX-NNN:` prefix.
- From MNX-132 (Identifier rename) on, merging `main` into `mc/26.1.2` conflicts on most files. So once MNX-132 lands, **1.21.1 takes bug fixes only**, ported by cherry-pick; new features go to `mc/26.1.2` first. This is the main recurring cost of the port.
- `mod_version` gets a Minecraft suffix on both lines (`0.5.0+1.21.1`, `0.5.0+26.1.2`) so a bug report says which line.

## Phases

### Phase A — Spike (now; vanilla only)

- **MNX-131** Build on 26.1.2 with `-Pvanilla` (no optional mods): toolchain, Identifier rename on a throwaway branch, compile error inventory, answer the client recipe question. Output: an error count per area and a corrected estimate in this file. Time-box: 2 days.

### Phase B — Core port (vanilla + JEI + KubeJS)

- **MNX-132** Toolchain and mechanical changes: Java 25, MDG/Gradle, no Parchment, `Identifier`, event and annotation renames, `UiFont` without reflection.
- **MNX-133** Recipe analysis on the new recipe API: `RecipeSources`, `RecipeEdges`, `RecipeFamilies`, `MaterialsCommand`; vanilla adapters (MNX-008/025) re-verified on 26.1.2 vanilla recipe JSON.
- **MNX-134** Reload and sync: reload listeners, generated pack injection, MNX-060 resync re-evaluated (removed if NeoForge sync no longer drops on a failing listener, otherwise rebuilt on the new sync path).
- **MNX-135** GameTests rewritten on the new framework, all 20 behaviors kept. Gate: no Phase B ticket merges a behavior change before its GameTest is back.
- **MNX-136** GUI on the render-state pipeline and input events; `UiShots` screenshots compared with 1.21.1 for every screen in `07-GUI.md`.
- **MNX-137** Client items: created items (ADR-019) tinted through client item definitions.
- **MNX-138** JEI adapter on JEI 26.1.2 with the client recipe solution from MNX-131; KubeJS bindings on KubeJS 8.

Exit: `./gradlew build test runGameTestServer` green with `-Pvanilla`, and with JEI + KubeJS; same generated pack (files and effects) as 1.21.1 on a vanilla world for the same policy files.

### Phase C — Content mods (gated)

Starts per mod when that mod has an **official** 26.1.2 build.

- **MNX-139** Recipe formats re-validated per mod (Mekanism, Create, IE, ... one commit each), dev pack rebuilt mod by mod in `gradle.properties`.
- **MNX-140** EMI adapter when an official EMI build exists (or decision to ship against the unofficial port, behind the adapter only).

## Release gate for 26.1.2

Ship a 26.1.2 build when Phase B exits **and** at least Mekanism and Create have official builds with re-validated formats. Before that, a 26.1.2 build may be published as alpha, labelled "vanilla + JEI only". `main` moves to 26.1.2 only when 26.1.2 packs outnumber 1.21.1 ones among Material Nexus users (CurseForge/Modrinth download split).

## Estimate

Measured by MNX-131 on `main` @ be4afdd (0.5.0): `./gradlew compileJava -Pvanilla` against NeoForge 26.1.2.126, JEI 29.53.0.115 and KubeJS 26.1.2-8.0.8, with the EMI adapter excluded. The toolchain (Gradle 9.2.1, MDG 2.0.148, foojay 1.0.0, Java 25, no Parchment) configures and decompiles with no change to the build logic.

`ResourceLocation` → `Identifier` is a plain rename: 1161 occurrences, including `FriendlyByteBuf.read/writeResourceLocation` → `read/writeIdentifier`. `Identifier` keeps `fromNamespaceAndPath`, `parse`, `tryParse`, `withDefaultNamespace` and `CODEC`. After it, javac reports **246 errors**. That count is a floor, because an unknown type hides every call made through it. Also renaming `GuiGraphics` → `GuiGraphicsExtractor` brings it to **412**:

| Area | Errors | What they are | Kind |
|---|---|---|---|
| GUI (`client/`) | 312 | 223 × `drawString` → `text` (same arguments); 16 × `renderOutline`; 10 × `pushPose`/`popPose` (pose is now a `Matrix3x2fStack`); 13 input overrides (`MouseButtonEvent`, `keyPressed`); `Btn` must implement `extractContents`; `Font` constructor and final `font` field (`UiFont`); `MultiLineEditBox`; screenshot `grab`; `hasShiftDown`; `CreatedItemsClient` (4) | ~80 % mechanical |
| Recipes and data (`datapack/`, `command/`) | 48 | 12 × recipe ids are now `ResourceKey<Recipe<?>>`; `getIngredients`, `getResultItem`, `getOrderedRecipes`, `getRecipeManager` gone; 4 reload listeners (`apply` signature, `Gson` → `Codec`); `registryOrThrow`, `getTag`; `getPackVersion` | real work |
| Reload listeners | 11 | `AddReloadListenerEvent` gone (also counted in their files' areas) | low |
| GameTests | 28 | `@GameTest`, `@GameTestHolder`, `PrefixGameTestTemplate` gone. Floor only: the test bodies are not checked until the new framework compiles | rewrite |
| Network | 16 | `PacketDistributor.sendToServer` moved; 13 × `ServerPlayer.server` now private | mechanical |
| Permissions | 4 | `hasPermissions(int)` / `hasPermission(int)` gone (commands, packet validation) | small, security-relevant |
| Items, core, integration | 9 | `InteractionResultHolder` gone (`NexusTerminalItem`); `ItemStack` from a holder; KubeJS 8: 1 error; JEI: 2 | low |

Not measured: test sources (`compileTestJava` does not run while main fails), anything hidden behind the GameTest framework, runtime behavior.
